1) Séparer le developpements en cours et la versions stable évite de créer des bug et soucis dans la versions stable. La dev permet de faire
des test, des fonctionnalités sans inquiétudes et repérer les erreurs avant qu'elle n'atteigne un point sensible (GIRARD Axel)

2) Il est nécessaire d'imposer une revue de code avant intégration pour vérifier le code et s'assurer qu'il n'y ai pas de conflit avec les fiches. (LEDUC Gabriel)

3) Un conflit Git se produit quand deux personnes modifient les mêmes lignes dans le même fichier mais sur des branches différentes. Quand on essaie de merge, Git voit deux versions différentes au même endroit et il sait pas laquelle garder, du coup il nous demande de régler ça nous-mêmes. (HAMDI Farès)

4) la différence entre les deux corrections est que la fix, la classique, se fait sans avoir d'impact sur la production, le dev peut prendre le temps de la faire sans soucis, cependant la hotfix, donc sur la prod, elle est urgente car c'est un bug qui est disponible en publique, qui se ressent sur le produit final. (GIRARD Axel)

5) Cela permet de maintenir la cohérence du code ainsi que de mieux anticiper et résoudre les conflits. (LEDUC Gabriel)

6) La branche de release c'est une branche qu'on crée quand on estime que develop est prête pour la production. On fait les dernières vérifs et petites corrections dessus, sans rajouter de features. Quand c'est bon on merge dans main avec un tag, et on reporte aussi les corrections dans develop. (HAMDI Farès)

7) le github project et issues peuvent permettre une meilleur organisations car ils permettent de regrouper des groupes de tâches ou problèmes sur lesquels se pencher, avec un status et une ou plusieurs personne(s) assignés à celles ci. (GIRARD Axel)

8) Pour retrouver l'origin d'une modification on peut regarder l'historique des commits (LEDUC Gabriel)
